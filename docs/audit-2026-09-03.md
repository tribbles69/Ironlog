### Architecture in one paragraph

One global mutable `S`; every screen is a function returning an HTML string, assigned to `#view.innerHTML`, then `wire()` re-binds every handler by querying `data-*` attributes. `save()` debounces 400 ms and writes the whole of `S` as one JSON string to one IDB key. There are no modules, no build step, no tests. Exercise identity is the display string. Meets are hard-wired to three keys (`squat`/`bench`/`deadlift`).

### Does the layout hold up?

The rendering pattern (string templates + `wire()`) will carry an Events picker and a first-run screen without trouble; it's simple and consistent. Four things do need to move first, in this order:

1. **Get the program out of `index.html` before the first-run screen or paid tier.** `boot()` auto-installs `IRONLOG_PROGRAM` on any state with no workouts/check-ins/meets (line 4948). Any new user — and you, after "Erase all data" — gets your 77-week plan and your two meets. It's also 343 KB every visitor downloads and the SW caches. Obvious shape: `program.json` fetched on demand, and a persisted "declined/removed" flag.
2. **Split the storage layer before sync.** One JSON blob under one key, rewritten on every keystroke (a fresh install with the program is ~372 KB of state before any training is logged). Sync needs per-record reads/writes; nothing else in the app cares how `S` is populated, so this is a contained change — `load()`/`flush()` are the only two touch points.
3. **Move `EX_DB` and `LOCAL_FOODS` to data files before the local-DB work.** Both are already the "local database" the plan describes; they just live inline. `EX_DB` (92 KB) and the 70-row food table are the seed. What's missing is an ID column — every lookup is by display string (see §3 B3 and §6).
4. **`meetCard`/`openMeet`/`attemptsFor` need de-hard-coding before Events.** Three fixed lift keys, `FIELDS` keyed by a regex on the meet name (`/west midlands|spring/` + `/93/`, line 2645), `liftName()` mapping index→`settings.priority`, `shortLift()` by substring. `meetCard` alone is ~150 lines of one template. An event-type picker means a schema `{type, lifts:[…]}` and these five functions rewritten against it; nothing else references meet internals.

The rest (Food, voice, analytics, calendar) can stay as it is.

## 2. Storage schema

### 2.1 Every persisted key

| Store | Key | Value | Written by | Read by |
|---|---|---|---|---|
| IndexedDB db `ironlog` v1, object store `kv` | `'ironlog.v1'` | `JSON.stringify(S)` — a string, not an object | `storePut()` ← `flush()` ← `save()` (400 ms debounce), `visibilitychange` (hidden), `pagehide` | `storeGet()` ← `load()` ← `boot()` — once per launch |
| localStorage | `'ironlog.v1'` | same string | `storePut()` **only when the IDB put throws** | `storeGet()` when IDB read throws **or returns null/undefined** (i.e. every fresh IDB) |
| localStorage | `'ironlog.anthropicKey'` | raw `sk-ant-…` | `setAiKey()` ← Settings → Save (removed when blank) | `aiKey()` ← `openSettings`, `parseFood`, `claudeParse`, `resolveVoiceSet` |
| Cache Storage | `'ironlog-v5'` | `./`, `index.html`, manifest, 3 icons (`sw.js`, `parse-food.js` not cached) | `sw.js` | `sw.js` |

Nothing in sessionStorage; no cookies. The key is **not** in the export and **not** cleared by "Erase all data".

Two-copies hazard: if a device ever wrote to localStorage (older build, or a session where IDB failed once), `storeGet` keeps preferring IDB and the localStorage copy silently goes stale. `load()` never reconciles them. *Unverified whether any device is in that state.*

### 2.2 Shape of `S` (`DEFAULT_STATE`, line 466) — exact

```
S = {
  settings, checkins[], workouts[], goals[], meets[],
  customEx[], exAliases{}, active, programs[], foods[]
}
```

`load()` does `Object.assign(clone(DEFAULT_STATE), parsed)` — **shallow**. A stored `settings` object replaces the default one wholesale, so any key added to `DEFAULT_STATE.settings` after a device first saved is absent (not defaulted) on that device. Today every such key is checked falsy-safely (`kcalTarget`, `proteinTarget`, `carbTarget`, `fatTarget`, `bars`, `plates`) so it's harmless; it stops being harmless the first time a new setting needs a non-falsy default (a first-run "seen" flag, a sync cursor).

| `sex` | `'male'\|'female'` | Settings | `dots`, `stdFor`, meets | |
| `bodyweight` | kg, `0`=unset | Settings | `bodyweightKg()` fallback | Duplicates `checkins[].weight` semantically (§2.4). |
| `priority` | `[squatName, benchName, dlName]` | `openPriority`, **`installProgram` (unconditionally)** | goals `total`, meets, tests, `liftName` | |

| `openerPct` | 50–100 | Settings | `openerPct()` | |

#### `checkins[]` — keyed by `date`, **no id**

Two writers produce two shapes for "empty":

| Field | From `openCheckin` (line 1452) | From `syncCheckinKcal` (line 3770) |
|---|---|---|
| `date` | `'YYYY-MM-DD'` | same |
| `weight` | kg, **`0`** when blank | **`null`** |
| `sleepH` | number\|null | null |
| `sleepQ`,`energy`,`soreness`,`stress` | 1–5 or **key absent** (spread of `undefined`, dropped by JSON) | `null` |
| `kcal` | user-typed number\|null | `Math.round(Σ foods.kcal)` or null |
| `notes` | string | `''` |

Readers: `checkinFor`, `bodyweightKg` (filters `weight > 0`, so both empties are safe), `last7`, `streak`, Home, calendar day panel. Replace-on-save: `S.checkins = filter(≠date); push(rec)` — whole-record last-writer-wins, order not preserved.

#### `workouts[]` — keyed by `id`; **six shapes share the array**

Common: `{ id, date, name, status, exercises:[{ name, notes, sets:[{ w(kg), r, rpe(number|null), done, warm }] }] }`

| Variant | `status` | Extra fields | Creator |
|---|---|---|---|
| planned (planner) | `'planned'` | — | `openPlanner` save; `id = uid()` |
| planned (program) | `'planned'` | `prog`, `block` | `installProgram`; `id = '<programId>#<index>'` (deterministic) |
| active | `'active'` | `start`, `plannedFrom?`, plus whatever the source had (`prog`, `block`, `srcId`, `tested` survive `structuredClone`) | `newBlank`, `startPlanned` (keeps planned id), `repeatWorkout` (new id). Lives in `S.active`, not the array. |
| completed (live) | `'completed'` | `source:'logged'`, `start`, `end`(ms), `summary:{mins, prs:[{name,w,r,e1, first?\|prev?}], volume}` | `finishWorkout` builds a **fresh object** — `prog`/`block` are dropped |
| completed (backfill) | `'completed'` | `source:'backfill'`, `end`, `summary{mins:0, prs:[], volume}`, keeps `prog`/`block`; sets filtered to `done` | `backfillPlanned` |
| completed (test) | `'completed'` | `source:'logged'`, `tested:true`, `notes`, `start:null`, `end` | `logTest` |
| completed (import) | `'completed'` | `source:'imported'`, `srcId:'liftoff:<date>'`, `name:'Liftoff import'`, `start:null`, `end`, `summary{mins from CSV, prs:[], volume}` | `importLiftoff` |
| legacy | any | `backfilled: true` (pre-0.3.0) | migrated to `source` in `load()` **only** — not on JSON import (§3 B7) |

`summary.*` is a snapshot computed once and never recomputed (§3 B5). `totalVolume()` recomputes from sets everywhere else, so two volume figures exist per workout (they agree today because both use done ∧ !warm, but import's `summary.volume` includes warm sets — imports never mark warm, so no visible difference).

Readers of note: `historyFor` (completed ∧ done ∧ !warm ∧ w>0 ∧ r>0 — so **zero-weight sets are invisible to all stats**), `allExercises` (names from *all* statuses, including 327 planned program sessions), calendar, Home, Analytics, `programStats`, `importCollisions`.

#### `goals[]` — keyed by `id`

`{ id, type:'lift'|'total'|'bodyweight'|'sessions'|'custom', exercise, name, target (kg, or count for sessions), deadline (''|ISO), since (ISO), startVal, current? }`. `current` is read for `custom` goals (`goalCurrent`) but **nothing ever writes it** (§3 B12).

#### `meets[]` — keyed by `id`

`{ id, name, date, fed, loc, wclass, bwTarget(kg|0), notes, lifts:{squat,bench,deadlift}(kg), attempts:{squat:{o,s},bench:{o,s},deadlift:{o,s}}, pct:{o,s}, prog?, attemptsLocked? }`. Program meets are copied in with a **fresh `uid()` per install** and de-duplicated only by `name+date` at install time.

#### `foods[]` — keyed by `id`

`{ id, date, meal:'Breakfast'|'Lunch'|'Dinner'|'Snacks', name, serving, kcal, p, c, f, fib, src:'ai'|'manual'|'offline' }`. No time-of-day, no created timestamp. The parser contract uses `{protein, carbs, fats, fiber}`; `addParsed` renames to `{p,c,f,fib}` — two shapes for one record.

#### The rest

- `customEx: string[]` — names picked from `EX_DB`, typed new, or created by import. Partly derived: `allExercises()` also harvests names from `workouts`, so a name can be "custom" in two ways.
- `exAliases: { rawLiftoffName: ironlogName }` — written by `importLiftoff` only when the mapped name differs; read by `matchExercise`.
- `programs: string[]` of program ids; only meaning is `programInstalled()`.
- `active: workout | null` — device-local live session, persisted in the same blob.

### 2.3 Identity and naming: where the same "thing" exists under several keys

Exercise identity is a **display string**, and eight independent name spaces are joined by exact string equality:

`LIB` (53) · `EX_DB` (736) · `EX_MUSCLE`/`EX_EQ`/`STD` (53, same strings as LIB) · `VOICE_ALIASES` targets · `IRONLOG_PROGRAM` names (40, **25 of which are in neither LIB nor EX_DB**: Smith Calf Raise, Hex Deadlift, DB Lat Raise, Flat DB Press, Sled Leg Press, Seated Cable Row, Strict Press, Rope Pushdown, Smith Shrug, Smith Shoulder Press, Machine Chest Press, Hip Abduction/Adduction, Cable Lat Raise, Bench Pin Press, …) · `customEx` · `exAliases` · every `workouts[].exercises[].name`.

Any two of these disagreeing on a movement produces two histories, two PR lines, two Analytics rows. This is the root of §3 B2/B3 and the main thing the local exercise DB has to fix (an ID per movement, names as aliases).

### 2.4 Same data held twice

| Data | Place A | Place B | Direction |
|---|---|---|---|
| Daily calories | `foods[]` (source) | `checkins[].kcal` | `syncCheckinKcal` overwrites B from A on every food change; user can also type B directly in the check-in modal and it's silently replaced next time food changes. |
| Bodyweight | `checkins[].weight` | `settings.bodyweight` | fallback only, but both flow through `bodyweightKg()`; a meet's `bwTarget` is a third. |
| Default bar | `settings.bars[0].kg` | `settings.barKg` | B is mutated by the ramp and plates dialogs independently of A. |
| Per-workout volume/PRs/mins | `summary.*` (frozen) | recomputed from sets (`totalVolume`, `statsFor`) | A never refreshed. Analytics "PRs all time" and calendar chips use A; everything else uses B. |
| Program | `window.IRONLOG_PROGRAM` (HTML) | copies in `workouts[]`/`meets[]` after install | edits to the program file don't propagate; ids are index-derived so a reordered regen would duplicate. |
| Backfill flag | `backfilled: true` (legacy) | `source` | migrated on load only. |
| State blob | IDB `ironlog.v1` | localStorage `ironlog.v1` (if ever written) | never reconciled. |
| Meal list, parser prompt, model id | `index.html` (`MEALS`, `FOOD_SYSTEM`, `claude-haiku-4-5-20251001`) | `parse-food.js` (`MEALS`, `SYSTEM`, `claude-haiku-4-5`) | drifted (§4). |

## 3. Bugs

### Blocks planned work

**B1 — The bundled program auto-installs on any "fresh-looking" state, and re-installs after you remove it.**
`boot()` line 4948: if `!S.workouts.length && !S.checkins.length && !S.meets.length && !S.active` and the program isn't in `S.programs`, install. `removeProgram` deletes the id from `S.programs`; "Erase all data" resets `S` entirely. Either one on a device with no other training → next launch re-installs 327 sessions, two meets, and overwrites `settings.priority` (`installProgram` line 3069 does this unconditionally). Blocks the first-run screen (there is no state that means "user chose nothing") and the paid tier (every new user gets your plan). *Fix: persist an explicit program choice; never auto-install.*

**B2 — PR false positive, 12 Aug 2026, Smith calf raise 135 kg × 10. Confirmed cause: it was a "first time logged" PR, and that verdict is frozen. Name mismatch is real but is not what fired that day.**

Evidence, from code and commit history rather than assumption:

1. PRs are written in exactly three places, all comparing a set's `e1rm` to `statsFor(name).best.e1` over **completed** workouts: the tick handler (line 4404), `applyVoiceSet` (line 4923), and `finishWorkout` (line 2178–2185), which is the only one that persists — into `summary.prs`. Backfill and import both write `prs: []` and never flag anything.
2. `finishWorkout` line 2184: `if (!st) prs.push({…, first: true})`. An exercise with **no completed history** is recorded as a PR. The summary modal says "First time logged", but the calendar chip (`completedCard` line 1612) and the Analytics "PRs — all time" counter (line 2422) treat it exactly like a real PR.
3. On 12 Aug the app was one day old (`3d5fad7`, 11 Aug) and the Liftoff importer did not exist yet (`8e3dc78`, 29 Aug). So the only possible history for "Smith Calf Raise" was (a) nothing, or (b) backfilled program sessions. The program prescribes 180 × 10 for that lift on 15/24/29 Jul and 7 Aug (e1RM 240). Under v0.1.1's `statsFor` (`prSrc = real.length ? real : h`) a backfill would have set the best at 240, and 135 × 10 (e1RM 180, or 189 at the most generous RPE) cannot beat it. So (a): no history → `first: true` → chip. The Feb–Aug Liftoff history arrived later and **cannot retroactively clear a stored `summary.prs`** (B5).
4. The name-mismatch you suspected **is** a live defect, just a different one. `matchExercise` (line 3262) tries `exAliases` → exact normalised match against your log → exact normalised match against `EX_DB` → else fuzzy *suggestion* for the review screen. The program's name is `Smith Calf Raise`; `EX_DB` has `Smith Machine Calf Raise`. If Liftoff's raw name normalises to an `EX_DB` name, the importer resolves it silently (`how:'db'`), **does not show it on the review screen** (`reviewLiftoffNames` only reviews `m.name == null`), and counts it in the "matched your log exactly" figure. The fuzzy suggester would have proposed `Smith Calf Raise` (token overlap 0.75 ≥ 0.6) but never runs for `EX_DB` hits. Result: two histories. 25 of the 40 program names are outside LIB and EX_DB (list in §2.3), so this applies to a third of your lifts, not one. *I cannot see your CSV, so which names actually split is unverified.*

How to tell on the phone in ten seconds: Stats → search "calf". Two rows → the import split (B3). One row with 12 Aug still showing a gold chip → the stale first-time snapshot (B5). Both can be true at once. Also worth a glance while there: if imported weights look ~2.2× too low across *every* lift, `guessUnit` (line 3240) called a kg file "lb"; that would also produce false PRs, but you'd see it everywhere, not on one calf raise.

*Fix, one line: don't count `first:true` as a PR in chips/counters; recompute PRs from history rather than storing them; route EX_DB matches through the review screen when a fuzzy match to an existing log name scores ≥ 0.6.*

**B3 — Liftoff exact-match against `EX_DB` bypasses review and creates duplicate exercise identities.** Same mechanism as B2 point 4, stated as its own defect because it fires on every import, not just calf raises. Also: the review screen's headline "N names matched your log exactly" includes DB matches that did not match your log. Blocks the local exercise DB (identity has to be an ID, with the program's, Liftoff's and EX_DB's names as aliases of it) and makes sync worse (two devices could resolve the same raw name differently).

### Risks user data

**B4 — Zero-weight sets cannot be completed and are discarded.**
Tick handler line 4399: `if (!s.w || !s.r) return toast('Enter weight and reps first')`. `finishWorkout` line 2173 drops any done set with `w ≤ 0` and any exercise left empty. `applyVoiceSet` (confirm card, line 4901) requires `w > 0`. `historyFor` line 1010 ignores `w ≤ 0`. `backfillPlanned` line 3163 only marks `w>0 && r>0` sets done. Consequence: Pull Up, Chin Up, Dips, Plank, Hanging Leg Raise (all in `LIB`) and the program's Back Extension / Hanging Knee Raise prescriptions cannot be logged at all; a session of only bodyweight work returns "Log at least one set first". The program file has **662 prescribed sets with `w=0` or `r=0`** (bodyweight and AMRAP rows) that a backfill silently deletes. Severity: medium — data the user entered is dropped without a message.

**B5 — `summary.prs` is a one-time snapshot.** Written only in `finishWorkout`. Never touched by import, backfill replacement, workout deletion, set edits, or the `prCountEst` toggle. Analytics "PRs — all time" is `Σ summary.prs.length`, so it counts first-time entries, counts PRs later superseded by imported history, and drops to zero for imported sessions. `viewCompleted`'s delete warning ("PRs from it will be removed") is true for that workout only.

**B6 — Two PR checks disagree on RPE.** The live tick (line 4404) and voice path (line 4923) compare `e1rm(w, r, rpe)`; `finishWorkout` (line 2180) compares `e1rm(w, r)` **without** rpe — but against `st.best.e1`, which *was* computed with rpe (`historyFor` line 1011). A set logged at RPE 8 can toast "★ PR" during the session and not appear in the summary or chip; the reverse can happen for a prior session logged at RPE 6. Low–medium; confusing rather than destructive.

**B7 — JSON import skips migration and validation.** Line 3699: `S = Object.assign(clone(DEFAULT_STATE), data)` with only `data.workouts` checked. The `backfilled → source` migration runs only in `load()`, so after importing an older export, backfilled sets are treated as real (`est: false`) until the app is next reloaded. Nothing checks that `exercises`/`sets` are arrays; a hand-edited file throws inside `render()` after the state is already replaced and saved.

**B8 — Food logging fabricates check-ins.** `syncCheckinKcal` pushes a stub check-in (all nulls) for any day with food. Home then shows "Logged for today" with an Edit button and four "—" tiles; `streak()` counts it; a manually entered check-in `kcal` is overwritten on the next food change. Deleting the check-in leaves the foods, so the next food edit resurrects it.

**B9 — Shallow state merge in `load()`** (§2.2). Latent: will bite the first new setting that needs a true default.

**B10 — Exercise names reach `toast()` via `innerHTML` unescaped** (lines 4405, 4923–4924, 4340). Names come from the picker, the CSV importer ("Keep as new" keeps the raw string) and the JSON importer. A crafted name executes script on the origin and can read `ironlog.anthropicKey`. Self-inflicted on a single-user app; becomes a real concern with shared programs or a server key. *Fix: `esc()` in those three calls, or make `toast` use `textContent`.*

**B11 — `pagehide` flush is async.** `flush()` awaits an IDB put; on `pagehide` the page can be torn down first. `visibilitychange` usually fires earlier and mitigates. *Unverified* how often it loses the last edit in practice.

### Untidy

**B12** — Custom goals can never progress: `goalCurrent` reads `g.current`, nothing writes it. 
**B13** — `programStats.done` only counts backfilled sessions, because `finishWorkout` builds a fresh object without `prog`. "Completed from this plan" is wrong once you train live. 
**B14** — `openFoodEntry(existing)` (edit) is never called with an item; only delete is wired. Food tab copy says "Everything is editable after." 
**B15** — Food modals close with `bg.remove()` (lines 4228, 4249) instead of `closeModal()`, leaving a dead entry in `modalStack`; the next Escape press is swallowed. 
**B16** — On GitHub Pages, every keyless parse first POSTs to `/.netlify/functions/parse-food`, gets a 404 HTML page, then falls back to the table. Wasted round-trip and, on a slow link, a wait. 
**B17** — `toast(…, 'good')` (lines 4159, 4169): no `.toast.good` rule exists; the rest of the app uses `'green'`. 
**B18** — `repeatWorkout` copies `prog`, `block`, `srcId`, `tested` into the active session (harmless today because `finishWorkout` rebuilds, but `S.active` is persisted with them). 
**B19** — `foodHistoryCard` always shows the 7 days ending *today*, regardless of the day being viewed.

## 4. Merge debris (calorie tracker fold-in)

Ranked by how much they'll get in the way of the server-side key and local food DB.

1. **Two complete parsers for the same job, drifted.** Client `claudeParse` (line 4085; prompt `FOOD_SYSTEM`, model `claude-haiku-4-5-20251001`, `max_tokens` 1024, no prefill, no input cap, output coerced loosely in `addParsed`) vs server `parse-food.js` (prompt `SYSTEM`, model `claude-haiku-4-5`, 1200, `[` prefill, input clipped to 1000 chars, output sanitised: 25 items max, name ≤ 80, serving ≤ 40, meal validated, non-finite → 0). The prompts give different instructions ("UK products and portion sizes" vs "cooked weight unless stated"; meal guessed from wording vs from time words). The server one is the better contract and is the one that should survive the move; the client one is what actually runs.
2. **Calories have two front doors.** Check-in modal "Calories (optional)" (pre-Food) and the Food tab, joined by `syncCheckinKcal` overwriting one with the other (B8). One has to go or become read-only.
3. **Netlify assumptions in a Pages app.** `netlifyParse`, the README's deploy guide, and five `parseError` branches (`ANTHROPIC_API_KEY is not set… redeploy`, `upstream 4xx`) describe a host this repo doesn't run on. The 404 branch tells the user to "add your own API key" — the opposite of the paid-tier direction.
4. **`MEALS` duplicated** in `index.html` and `parse-food.js`; **`guessMeal()`** (clock-based, client) duplicates the prompt's meal inference and only applies to the offline table.
5. **Different modal convention** (`bg.remove()`, B15), different toast class (`'good'`, B17), `label`s outside `.field` wrappers, `onOpen(bg) {}` method shorthand — the Food block was clearly written against a different shell. Cosmetic except B15.
6. **Field-name translation at the boundary** (`protein→p`, `carbs→c`, `fats→f`, `fiber→fib`) exists only because the stored shape came from the old app and the parser contract from the new one. Pick one before the local food DB adds a third.
7. **Nutrition targets** live in `settings` but are edited from the Food tab, not Settings; `DEFAULT_STATE` documents `src:'ai'|'manual'` but the code also writes `'offline'`.
8. **Unreachable edit path** (B14) — likely existed in the old app's wiring and didn't make it across.

## 5. Secrets and API calls

### Where the key lives now

- `localStorage['ironlog.anthropicKey']`, plain text, per origin. Entered in Settings (line 3586) into a `type="password"` input whose `value` attribute is pre-filled with the key — so it's in the DOM every time Settings opens.
- Readable by any script on the origin (see B10). Not in the JSON export. Not removed by "Erase all data" (only by clearing the field or clearing site data).
- `parse-food.js` expects `process.env.ANTHROPIC_API_KEY` on Netlify — not deployed here.

### Every call site

| # | Function | Endpoint | Auth | Sends | Triggered by |
|---|---|---|---|---|---|
| 1 | `claudeParse(text, FOOD_SYSTEM)` line 4085 | `POST https://api.anthropic.com/v1/messages` | `x-api-key` from localStorage + `anthropic-dangerous-direct-browser-access: true` | model `claude-haiku-4-5-20251001`, `max_tokens 1024`, system prompt, one user message = the raw food text | `parseFood()` when a key is set |
| 2 | `claudeParse(text, SET_SYSTEM)` via `claudeParseSet` line 4859 | same | same | same shape; user message = the speech transcript | `resolveVoiceSet()` only when the local grammar fails **and** a key is set |
| 3 | `netlifyParse(text)` line 4128 | `POST /.netlify/functions/parse-food` (same origin) | none | `{text}` | `parseFood()` when no key — 404 on Pages |
| 4 | `parse-food.js` (server) | `POST https://api.anthropic.com/v1/messages` | env var | model `claude-haiku-4-5`, `max_tokens 1200`, `SYSTEM`, user text ≤ 1000 chars, assistant prefill `[` | would be reached by #3 on Netlify |

Nothing else leaves the device: no history, no identity, no bodyweight, no exercise names (the voice path sends the transcript, which may contain an exercise name). Speech recognition itself may go to Google's servers when the on-device model isn't available (`_voiceMode === 'cloud'`) — that's the browser, not this code, but it's the other network egress.

### What has to move server-side for a paid tier

- Both prompts (`FOOD_SYSTEM`, `SET_SYSTEM`) and the model choice — one endpoint with `{kind:'food'|'set', text}` or two endpoints. `parse-food.js` already has the food half, including the input cap and output sanitiser; **there is no server equivalent for the set parser**, and the client-side `addParsed` sanitiser is weaker than the server one.
- An identity. There is none anywhere in the app — no account, no device id, no token. Rate limiting and metering need one; this is the same identity sync needs (§6), so design them together.
- Client changes: delete `aiKey()/setAiKey()` and the Settings field; the branch `aiKey() ? claudeParse : netlifyParse` (line 4153) and the `if (!aiKey())` bail-out in `resolveVoiceSet` (line 4826) both become "call the proxy, else offline table"; `parseError` needs rewriting around the proxy's error shape; drop the `anthropic-dangerous-direct-browser-access` header (it's only needed for direct browser calls).
- Keep `estimateOffline` and `parseSetSpeech` as the no-network path — they're the reason the app works in the gym, and nothing about them needs to change.
- The service worker's `fetch` handler ignores cross-origin and non-GET requests, so a same-origin `/api/...` POST passes through untouched; a different-origin proxy needs CORS on the server, nothing on the client.

## 6. Sync blockers

Ranked by what breaks first once two devices share a log.

1. **One blob, one key.** The unit of persistence is all of `S` (≈ 372 KB with the program installed, before any training). There is no per-record write, no dirty tracking, no version. Sync as-is means shipping the whole state on every keystroke or diffing on the client; either way the storage layer (`load`/`flush`, ~40 lines) has to become a record store first. Everything below assumes that.

2. **No timestamps on anything except live workouts.** `workouts.start/end` exist only for `source:'logged'` sessions (tests and imports set `start:null`). `checkins`, `goals`, `meets`, `foods`, `customEx`, `exAliases`, `settings` have no `createdAt`/`updatedAt`. Without them, conflict resolution can't even do last-writer-wins.

3. **No tombstones.** Every delete is `S.x = S.x.filter(…)`. Device A deletes a session; device B, which still has it, syncs it back. Applies to workouts, check-ins, goals, meets, foods, and to `removeProgram` (327 filtered records).

4. **Records without an id: `checkins[]`.** Keyed by `date` and replaced wholesale on edit. `date` is a usable natural key, but two devices editing the same day's check-in (one adding sleep, one adding weight) lose one side entirely; and the food-generated stub (B8) will fight the manual one across devices.

5. **Exercise identity is a string, resolved per device.** `matchExercise`, the picker's `customEx.push`, and `exAliases` are all local decisions. Two devices importing the same CSV can map `"Smith Machine Calf Raise"` differently, and there is no way to merge two histories after the fact. This is the local-exercise-DB work again: stable exercise ids, names as aliases, before sync.

6. **Derived data persisted as if it were source.** `summary.prs/volume/mins` (B5), `checkins.kcal` (from foods), `customEx` (partly from workouts), `settings.barKg` (from bars). Syncing these creates conflicts that aren't real; recompute on read instead.

7. **Device-local state mixed into user data.** `active` (a live session — must not be merged, or must be single-writer), `settings.units`, `settings.voiceLocalDeclined`, `settings.barKg`, `settings.handle`. Needs a split into `profile` (synced) vs `device` (not).

8. **`uid()` is 8 chars of `Math.random()` base-36** (~41 bits), no device prefix, no time component. Collisions across devices are unlikely but not impossible over a long log; the bigger issue is that ids aren't sortable and carry no provenance. Program ids `'<program>#<index>'` are deterministic (good — two devices installing the same program converge) but break if the program file is ever regenerated with a different order. Program **meets** get a fresh `uid()` per device (bad — two devices, two copies of each meet, deduped only at install time by `name+date`).

9. **Boot-time auto-install races sync** (B1). A second device boots empty → installs the program → then receives the first device's state. Workouts converge on ids; meets, `settings.priority`, and any program the first device had removed do not.

10. **Ordering is positional.** Same-date workouts render in array order; `importLiftoff` re-sorts the whole array; `startPlanned` keeps the planned id and moves the date. There is no `seq`/`order` field to reconcile.

11. **Whole-record replacement everywhere** (`filter(≠id); push(rec)`): goals, meets, check-ins, planner saves. Field-level merges (device A edits a meet's notes, device B its date) need per-field timestamps or the edit-in-place pattern the Food tab already uses (`Object.assign(existing, rec)`).

12. **`srcId: 'liftoff:<date>'`** is a good natural key for imports and should be kept; but a corrected re-export of the same date is refused forever ("already imported"), and there is no way to replace an import short of deleting sessions one by one.

Things that already help: kg-only storage; ISO dates everywhere; `workouts.id` on every session; `source` three-way flag; deterministic program ids; `exAliases` being a map rather than a list.
